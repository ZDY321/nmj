# 第二批优化的浏览器测量（2026-11-06）

本记录对应分钟问候语隔离、学生课程索引、出勤/核对键合并，以及课节更新入口的优化。原始样本保存在同目录的 `2026-11-06.json`。

## 环境与方法

- Windows，Node 24.14.0，Edge 156.0.4314.58，1440×1000，Asia/Shanghai。
- 使用实际应用的 Vite 开发模式和 React StrictMode。页面渲染计数由专用 Vite 配置注入；正常开发/生产构建不包含这些计数。
- 三种完全合成的档案分别包含：40/12/240、240/80/1800、800/240/3600 名学生/门课程/个课节。没有教务核对历史、反馈记录和补课关联；复杂补课由单元对照测试覆盖。
- Playwright 创建独立浏览器上下文。所有 API 都由内存响应处理，其他源的请求被阻止。出勤修改调用真实页面和加密保存代码，随后解密模拟服务端收到的档案，核对修改后的出勤状态及版本条件。
- 页面操作计时包含自动化动作等待及两个动画帧；首次打开还包含开发服务器的懒加载和编译，不能当作生产首屏性能。不同运行有机器负载和动画调度波动。
- 组件的 commitMs 是“组件函数开始至布局 effect”的累计时间，包含子组件，并非 React Profiler 的自身执行时间。StrictMode 会额外调用渲染函数；记录 2 次调用通常对应 1 次提交。
- 空闲计数使用虚拟时钟快进一分钟，仅验证有无渲染，不使用快进期间的耗时。其余计时分辨率约为 1ms，记录为 0ms 表示低于计时分辨率。

## 页面结果

下面保留小/中档案的完整优化前后结果，不筛掉变慢的单次样本。搜索取五个不同关键词的中位数；其余是一次完整运行的结果。单位 ms。

| 操作 | 小档案：前→后 | 中档案：前→后 |
| --- | ---: | ---: |
| 打开排课页 | 2356 → 2345 | 3489 → 1398 |
| 切换课程记录 | 352 → 361 | 1289 → 478 |
| 修改一个学生出勤（到下一次绘制） | 424 → 353 | 2349 → 818 |
| 打开学生页 | 1023 → 1006 | 343 → 489 |
| 搜索学生，中位数 | 111 → 104 | 130 → 123 |
| 编辑个人备注至模拟服务端收到保存 | 980 → 984 | 1048 → 1056 |

空闲一分钟，优化前 App 和当前 ScheduleView/StudentsView 各新增 2 次调用、1 次提交；优化后各为 0。三种规模均验证通过。问候语按原时区和原时间边界变化，跨午夜仍保留日期刷新。

800 名学生/3600 课节的原版在 30 秒超时前调用 ScheduleView 42 次，提交 0 次，停在“正在加载”。移出循环内的 todayIso 和 weekDatesFor 计算后，测试能够完成；最终打开排课页测得 4098ms。该结果只说明此合成场景恢复可用，不表示所有大档案卡顿已解决。最终单次出勤操作仍约 3207ms，后续应继续分析排课页派生计算与保存状态更新。

大档案学生搜索的单独对照：先只完成问候语和排课日期计算调整，再加入学生索引。前一阶段搜索中位数 317ms，最终 122ms；StudentsView 渲染至布局 effect 中位数 152ms → 61ms。该对照的起点是中间版本，不是完整优化前版本。

## 普通课节批量更新

在同一浏览器中分别运行原 App 算法和 applyLessonUpdates，修改 200 个普通课节，各 5 次。计时之外克隆输入，并逐次比较完整档案 JSON 相等；不包括深拷贝、React、加密或上传。

| 总课节数 | 原算法中位数 | 新算法中位数 |
| ---: | ---: | ---: |
| 240 | 3ms | <1ms |
| 1800 | 18ms | 1ms |
| 3600 | 34ms | 2ms |

普通批次由反复全表 find/map 改为局部索引及一次替换；涉及原课与补课、待补学生、修改关联、重复修改时仍使用原顺序算法。11 个对照测试覆盖：普通批量、重复 ID、不存在的课节、空 ID/空关联、原课与补课不同修改顺序、补课删除/名单缩减、取消的补课及费用快照。

## 保存成本

下表是优化后每项 5 次的中位数。encryptJson 包含 PBKDF2 密钥派生、JSON 编码、AES-GCM 和 Base64 转换，不是单独的 AES 时间。本地写入包含加密结果序列化和替换已有缓存。

| 规模 | JSON 字节数 | structuredClone | JSON 序列化 | encryptJson | 本地缓存写入 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 小 | 162698 | 2ms | 1ms | 139ms | 1ms |
| 中 | 1219408 | 17ms | 3ms | 192ms | 8ms |
| 大 | 2528275 | 39ms | 7ms | 363ms | 16ms |

真实网络上传、信任设备缓存与连续多次编辑尚未独立测量。代码检查发现 schedulePersist 在防抖上传前仍会立即序列化并写入解锁会话，后续应单独量化写入次数。当前证据不足以决定改动加密格式、密钥策略或云端文档分区，本批保持保存架构。

最初 6000 课节的探索样本出现云端读取失败提示，尚未独立定位，可能涉及本地缓存额度；已从前后对比中排除。大规模档案容量边界仍是后续检查项。

## 复现

安装项目依赖后，在 PowerShell 中运行（默认使用本机 Edge）：

~~~powershell
$env:BENCHMARK_LABEL = "current"
npm run benchmark
~~~

本机使用 Chrome 时设置 BENCHMARK_BROWSER=chrome；其他机器需具备对应浏览器。BENCHMARK_LABEL 只用于分开存储结果；测试没有自动切换旧源码。使用 before 标签会关闭空闲零渲染断言，专供复跑旧版本。

运行结果在 artifacts/performance/<label>/，已加入忽略规则。提交审查用的样本保存在本目录。npm run check 同时检查应用和性能脚本。
